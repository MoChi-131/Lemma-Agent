# Lemma Agent 交接文件

**交接日期：2026 年 11 月 16 日**

## 一、專案概況

Lemma Agent 是用於 Supermama 飛書（Lark）知識檢索與文件發布的 MCP 服務，提供知識搜尋、文件內容讀取、外部來源白名單檢查，以及經使用者批准後建立 Wiki 文件等功能。

## 二、版本與部署狀態

| 版本／來源 | 目前狀態 | 交接注意事項 |
| --- | --- | --- |
| Penny 的 `main`（Penny-main） | 舊版本，已過時 | 僅供歷史參考，後續開發應以較新版本為基礎 |
| 來自 MoChi `main` 的 Pull Request 版本 | 目前部署於 AWS 的版本 | 作為現行服務與回歸測試的比較基準 |
| v1.2（`MoChi/feature/v1.2.0-mcp`） | 目前最新的開發版本 | 尚需完成回歸測試，確認功能穩定後再安排部署 |

上述 AWS 部署狀態依本次交接資訊記錄；接手時應補上對應的 **PR 連結、部署 commit、AWS 服務位置及部署日期**，方便追蹤與回滾。

## 三、v1.2 主要改進

依目前專案 [README](../../README.md)，v1.2 的主要更新包括：

1. **整合官方 Lark MCP**：引入固定版本的 `@larksuiteoapi/lark-mcp@0.5.1`，透過內部 stdio worker 處理相關 Lark 操作。Lemma 繼續負責知識治理規則、資源處理及對外工具介面。
2. **改善日誌與故障追蹤**：統一日誌格式，加入工具執行結果、處理時間、部分結果警告及錯誤 webhook 通知，並遮蔽敏感資訊。
3. **新增服務就緒檢查**：除既有 `/health` 外，新增 `/ready`，檢查必要的 App ID／Secret 是否已設定。此檢查不代表 Lark 授權或實際資料存取已成功。
4. **增加針對性驗證**：提供官方 MCP 整合、日誌、文件發布及 Wiki 子樹讀取等測試，供版本驗證與問題排查使用。

**v1.2 尚未完成正式環境的逐使用者 OAuth 身分驗證。**

## 四、待辦事項：回歸測試

下一步是確認 v1.2 在改用官方 Lark MCP 後，既有功能仍能正常運作，並與目前 AWS 版本比較結果。

| 測試範圍 | 驗證重點 |
| --- | --- |
| MCP 連線 | 初始化、工具呼叫、斷線重連及服務重啟後的連線 |
| 知識檢索 | Metadata 搜尋、來源資格判斷及 Wiki fallback |
| 文件讀取 | 文字、表格、嵌入式 Sheets、PDF、圖片及白板 |
| 治理規則 | 未符合資格的來源是否被阻擋；外部網址是否按白名單處理 |
| 文件發布 | 使用者批准流程、指定位置建立及建立後讀回驗證；使用測試位置執行 |
| 異常處理 | 權限不足、憑證錯誤、逾時及部分結果是否清楚回報 |
| 日誌與通知 | 錯誤是否可追蹤，且不洩露憑證或文件內容 |

在 repository 根目錄先執行現有離線測試：

```sh
npm test
npm run test:knowledge-registry
npm run test:official-mcp
npm run test:logging
npm run test:document-publication
npm run test:wiki-subtree:mcp
```

離線測試通過後，仍需以實際 Lark 資源及遠端 MCP connector 進行端到端驗證。測試結果應記錄使用版本、案例、預期結果、實際結果及未解決問題。本交接文件不代表上述測試已執行或通過。

## 五、已知安全問題與下一版本方向

目前服務缺少應用層的使用者身分驗證。依現行部署情況，**任何取得服務連結的人都可能連線並使用服務**；可存取的資料及可執行的操作，取決於後端 Lark 應用程式權限與服務設定。

下一版本應優先評估並導入 OAuth，涵蓋：

- 使用者登入，以及允許使用服務的人員範圍。
- 每次請求的 token 驗證、到期及撤銷處理。
- 使用者身分與 Lark 資料權限的對應。
- 未登入、未獲授權及 token 失效時的拒絕存取測試。

需特別區分 **MCP 服務入口的登入驗證**與 **Lark 資源的存取授權**，兩者都需要明確設計。目前的 `LEMMA_LARK_USER_OAUTH` 僅供本機單一使用者寫入測試，不能直接視為正式環境的多人 OAuth 方案。

## 六、建議接手順序

1. 記錄目前 AWS 部署版本的 PR、commit 與部署設定。
2. 完成 v1.2 回歸測試，修正問題並保存測試紀錄。
3. 確認部署與回滾步驟，再安排更新 AWS。
4. 下一版本優先處理 OAuth 與存取權限控制。
